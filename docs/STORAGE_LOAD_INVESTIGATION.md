# گزارش بررسی: «بعد از ورود، اطلاعات پرسنل لود نمی‌شود»

تاریخ: ۲۰۲۶-۰۸-۲۱
نتیجهٔ کلیدی: **مشکل از سمتِ «بارگذاری داده از فضای ذخیره‌سازی ابری (S3)» است، نه از منطق برنامه‌ریزی/حل‌کننده.** کل سیستم (۶۵۸ تست منطقی + ۱۰ تست مسیر ذخیره‌سازی) سالم است؛ اما اگر `GET /api/storage` با خطای ۵۰۳ جواب دهد، نسخهٔ قبلی رابط کاربری **هیچ پیام خطایی نشان نمی‌داد** و صفحهٔ «عادی ولی خالی» می‌ماند — دقیقاً همان چیزی که گزارش شده.

---

## ۱) معماری مسیر بارگذاری بعد از ورود

```
ورود (PostgreSQL / Prisma)  ←── موفق است (چون کاربر وارد می‌شود)
        │
        ▼
صفحهٔ اصلی → GET /api/storage?months=1404_5,1404_6,...
        │                          │
        │   requireCurrentUser()   │  (نشست معتبر است)
        ▼                          ▼
   readDatabaseState() ──► خواندن اسناد از S3 (سطل جدا برای هر محیط)
        │
        ├── departments/index.json
        ├── departments/{بخش}/personnel.json   ← نام و مشخصات پرسنل
        ├── departments/{بخش}/requests.json
        ├── departments/{بخش}/settings.json
        ├── departments/{بخش}/holidays.json
        └── departments/{بخش}/schedules/{ماه}.json ← برنامهٔ شیفت
        │
        ▼
   setPersonnel(...) / setSchedule(...) → نمایش در داشبورد
```

- ورود و احراز هویت در PostgreSQL انجام می‌شود؛ دادهٔ اصلی (پرسنل، درخواست‌ها، برنامه‌ها) در **Object Storage سازگار با S3** نگهداری می‌شود.
- این معماری **هیچ حالت جایگزین/Seed خودکار ندارد**: اگر S3 پیکربندی نشده باشد یا سندی گم شده باشد، `GET /api/storage` عمداً با `503 STORAGE_UNAVAILABLE` جواب می‌دهد (سیاست «شکست بسته» در `docs/STORAGE_ARCHITECTURE.md`).
- متغیرهای محیطی لازم: `STORAGE_ENV` (بدون مقدار پیش‌فرض!)، `S3_ENDPOINT`، `S3_REGION`، `S3_ACCESS_KEY_ID`، `S3_SECRET_ACCESS_KEY`، `S3_BUCKET_DEVELOPMENT|STAGING|PRODUCTION`.
  - ⚠️ `.env.example` این متغیرها را ندارد؛ یک استقرار تازه از روی این مخزن بدون تنظیم دستی آن‌ها، **همیشه** داشبورد خالی می‌دهد.

## ۲) ریشهٔ مشکل: خطای بی‌صدا در کلاینت

در `app/page.tsx` (تابع `loadDatabase`)، پیش از این اصلاح:

- اگر `/api/storage` با ۵۰۳ جواب می‌داد، خطا فقط با `console.error` لاگ می‌شد؛
- سپس در `finally` پرچم‌های `isPersonnelLoaded` و `dbChecked` روی `true` می‌رفتند؛
- نتیجه: داشبورد کامل و «سالم‌نما» ولی **بدون هیچ پرسنلی و بدون هیچ پیامی** — حتی نقطهٔ «پشتیبان‌گیری ابری» سبز می‌ماند.

یعنی اگر S3 در محیط اجرا مشکل داشته باشد، کاربر دقیقاً همین علامت را می‌بیند: ورود موفق، چند ثانیه انتظار (تلاش مجدد خودکار `resilientFetch` روی ۵۰۳ تا ۳ بار)، و بعد… هیچ.

## ۳) سناریوهایی که بازتولید و تست شدند

تست جدید: `tests/storage-route-failure-modes.test.ts` — مسیر واقعی `GET /api/storage` را با شبیه‌سازی نشست و S3 ساختگی صدا می‌زند:

| # | سناریو (علت محتمل در محیط شما) | پاسخ API | وضعیت تست |
|---|---|---|---|
| ۱ | پیکربندی S3 تعریف نشده (env گم شده) | 503 `STORAGE_UNAVAILABLE`، `retryable:false` | ✅ |
| ۲ | سطل خالی (حتی بدون `departments/index.json`) | 503 `STORAGE_UNAVAILABLE` | ✅ |
| ۳ | بخشی که سند `personnel.json` ندارد (مهاجرت ناقص) | 503 `STORAGE_UNAVAILABLE` | ✅ |
| ۴ | بخش حساب کاربر از فهرست سطل حذف شده | 503 + «department does not exist in storage» | ✅ |
| ۵ | سه شکست پیاپی → مدارشکن باز (circuit breaker) | 503 با `circuit:"open"` + هدر `Retry-After` | ✅ |
| ۶ | سطل سالم و کامل | 200 + پرسنل و برنامهٔ ماه | ✅ |

اجرا: `npm run test:storage-route` (و در `npm test` عادی، ۴ تست لایهٔ ذخیره‌سازی همیشه اجرا و ۶ تست مسیر با پرچم module-mocking اجرا می‌شوند).

نتیجهٔ کل مجموعه: **۶۵۲ تست سبز، ۰ شکست** (به‌علاوهٔ ۱۰ تست بالا).

## ۴) چرا «قبل کار می‌کرد و حالا نه»؟

محتمل‌ترین علت‌ها به ترتیب:

1. **متغیرهای محیطی S3 در استقرار جدید تعریف نشده‌اند** (پس از redeploy / جابه‌جایی پلتفرم، env گم می‌شود). نشانه: خطای «STORAGE_ENV must be explicitly set…».
2. **سطل S3 خالی یا اسنادش پاک شده** (حذف دستی، expiration policy، اشتباه در نام سطل/prefix).
3. **مهاجرت به ذخیره‌سازی دانه‌ای (granular) انجام نشده** — نسخهٔ جدید فقط اسناد `personnel.json` و … را می‌خواند؛ دادهٔ قدیمیِ تک‌فایله باید با `npm run storage:migrate` منتقل شده باشد.
4. **بخشِ حساب کاربر از `departments/index.json` حذف شده** (حذف سخت بخش، بدون ساخت دوباره).
5. مدارشکن در فرایند سرور باز مانده (گذرا؛ با `Retry-After` خودش برمی‌گردد).

## ۵) تغییرات انجام‌شده در کد

1. **نمایش خطای بارگذاری** (`app/page.tsx`): اگر `GET /api/storage` ناموفق باشد، یک بنر قرمز با پیام فارسی، کد خطا (مثلاً `STORAGE_UNAVAILABLE`) و دکمهٔ **«تلاش دوباره»** نمایش داده می‌شود. بارگذاری موفق، بنر را پاک می‌کند.
2. **نقطهٔ وضعیت «پشتیبان‌گیری ابری»** در هدر هنگام خطا قرمز می‌شود.
3. **تست‌های بازتولید** (`tests/storage-route-failure-modes.test.ts`) + اسکریپت `npm run test:storage-route`.
4. **سازگاری با دادهٔ قدیمی** (`lib/legacy-compat.ts`): اسنادی که نسخه‌های قبلی
   در آروان نوشته‌اند (بدون فیلدهای جدید، با کلیدهای ناشناخته، رشتهٔ عددی و…)
   حالا با نرمال‌سازیِ فقط-خواندنی بارگذاری می‌شوند؛ ذخیرهٔ بعدی خودش آن‌ها را
   به قالب جدید ارتقا می‌دهد. کلاینت با `legacyNormalizedResources` مطلع می‌شود.
5. **بازیابی خودکار از snapshot قدیمی داخل سطل** (`lib/legacy-recovery.ts`):
   اگر `departments/index.json` وجود نداشته باشد اما snapshot تک‌فایلهٔ نسخهٔ
   قبلی داخل همان سطل باشد، `GET /api/storage` خودش آن را به اسناد دانه‌ای
   تبدیل می‌کند (نوشتن‌های create-only؛ index آخر از همه) و بارگذاری موفق می‌شود
   — هیچ دست‌زدنی در کنسول آروان لازم نیست.
6. **عیب‌یاب و مهاجرت خط فرمان** (فقط خواندنی / ایمن):
   - `STORAGE_ENV=<env> npm run storage:check` — گزارش کامل سطل: کدام سند
     هست/نیست/معتبر/قدیمی/خراب است + اقدام پیشنهادی.
   - `STORAGE_ENV=<env> npm run storage:migrate:s3` — مهاجرت snapshot داخل سطل.
7. **`.env.example`**: متغیرهای S3 اضافه شدند تا استقرار تازه بدون آن‌ها
   «ساکت» خراب نشود (پیش‌تر فقط در docs بودند).

## ۶) چک‌لیست عیب‌یابی روی سرور خودتان

```bash
# ۱) سلامت کلی (دیتابیس + مدارشکن ذخیره‌سازی)
curl -i https://<your-domain>/api/health

# ۲) متغیرهای محیطی روی سرور (باید موجود باشند)
echo $STORAGE_ENV $S3_ENDPOINT $S3_BUCKET_DEVELOPMENT $S3_BUCKET_PRODUCTION
#  → STORAGE_ENV هیچ مقدار پیش‌فرضی ندارد؛ حتماً development/staging/production است؟

# ۳) تست مستقیم مسیر داده (با نشست خودتان، از مرورگر یا curl با کوکی)
#    پاسخ 503 با code=STORAGE_UNAVAILABLE یعنی مشکل از S3 است، نه از کد برنامه.
#    پاسخ 200 یعنی داده موجود است و مشکلِ شما جای دیگری است (کش مرورگر/سرور).

# ۴) بررسی محتوای سطل (با mc یا کنسول S3):
#    nursingsmart/<env>/v1/departments/index.json
#    nursingsmart/<env>/v1/departments/<id>/personnel.json
#    nursingsmart/<env>/v1/departments/<id>/schedules/1404_5.json

# ۵) اگر تازه ارتقا داده‌اید و سطل خالی است: مهاجرت دادهٔ قدیمی
#    STORAGE_ENV=<env> MIGRATION_SOURCE_FILE=./legacy.json npm run storage:migrate

# ۶) آزمون سازگاری Conditional-Write پیش از استقرار
#    STORAGE_ENV=development npm run storage:test-conditional
```

## ۷) نتیجه‌گیری

- **کجای سیستم خراب است؟** در ناسازگاری نسخه‌ای: داده‌های موجود در سطل (که
  نسخهٔ قبلی نوشته) با اسکیمای سخت‌گیرانهٔ فعلی خوانده نمی‌شدند و خطا هم
  توسط رابط کاربری پنهان می‌ماند. نه آروان تغییر کرده و نه ورسل — کدِ جدید
  بود که دادهٔ قدیمی را «نمی‌فهمید».
- **چه چیزی خراب نبود؟** موتور زمان‌بندی، احراز هویت، و کل منطق سامانه — همهٔ تست‌ها سبزند.
- **حالا چه می‌شود؟** (۱) دادهٔ قدیمی با نرمال‌سازی خودکار خوانده می‌شود و با
  اولین ذخیره به قالب جدید ارتقا می‌یابد؛ (۲) اگر سطل هنوز snapshot تک‌فایلهٔ
  قدیمی دارد، `GET /api/storage` خودش آن را مهاجرت می‌کند؛ (۳) اگر باز هم خطایی
  بماند، بنر قرمز + `npm run storage:check` علت دقیق را نشان می‌دهند.
