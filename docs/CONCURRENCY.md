# معماری هم‌زمانی (Concurrency) در NursePlan

این سند توضیح می‌دهد سامانه چگونه در برابر خطاهای هم‌زمانی — قفل شدن پایگاه داده،
بن‌بست (deadlock)، درخواست‌های هم‌زمان و کلیک‌های سریع کاربر — محافظت می‌شود.

## خلاصهٔ مشکل

سه دسته خطا گزارش شده بود:

| علامت | ریشهٔ واقعی |
|---|---|
| «خطای قفل هم‌زمانی» / Deadlock | چند `await prisma...` پشت سر هم، بدون تراکنش؛ هر کدام یک تراکنش مستقل بود |
| «دیتابیس آماده نیست» | اختلال لحظه‌ای اتصال یا پر شدن connection pool، بدون هیچ تلاش مجدد |
| رکورد تکراری / «کد ملی تکراری» | الگوی «بخوان → تصمیم بگیر → بنویس» بدون قفل؛ دو کلیک سریع هر دو از شرط عبور می‌کردند |

## لایه‌های دفاعی

```
┌─ فرانت‌اند ──────────────────────────────────────────────┐
│ ۱. useSubmitGuard / قفل ref  → کلیک دوم در همان تیک بسته │
│ ۲. resilientFetch            → تلاش مجدد + Retry-After   │
│ ۳. generation + AbortController → پاسخ کهنه دور ریخته    │
└──────────────────────────────────────────────────────────┘
                          ↓
┌─ لایهٔ API ──────────────────────────────────────────────┐
│ ۴. withMutex(key)   → درخواست‌های هم‌کلید سریال می‌شوند   │
│ ۵. authErrorResponse → خطای گذرا با کد و Retry-After صحیح│
└──────────────────────────────────────────────────────────┘
                          ↓
┌─ لایهٔ پایگاه داده (lib/db) ─────────────────────────────┐
│ ۶. runInTransaction → خواندن+نوشتن اتمیک، با مهلت صریح   │
│ ۷. withDbRetry      → عقب‌نشینی نمایی + jitter           │
│ ۸. classifyDbError  → تفکیک خطای گذرا از خطای منطقی      │
└──────────────────────────────────────────────────────────┘
                          ↓
┌─ پایگاه داده ────────────────────────────────────────────┐
│ ۹. قید یکتایی (unique index) → ضمانت نهایی               │
└──────────────────────────────────────────────────────────┘
```

هیچ لایه‌ای به‌تنهایی کافی نیست: لایه‌های ۱–۵ فشار و تداخل را کم می‌کنند، اما
ضمانت نهایی درستی داده همیشه قید یکتایی و تراکنش پایگاه داده است (لایهٔ ۶ و ۹).
این موضوع به‌ویژه در استقرار **چندنمونه‌ای** اهمیت دارد، چون قفل و کش درون‌حافظه‌ای
فقط در همان پردازه معتبرند.

## ۱) مدیریت تراکنش‌ها

### قانون طلایی
> هر عملیاتی که بیش از یک نوشتن دارد، یا الگوی «بخوان → تصمیم بگیر → بنویس» دارد،
> **باید** داخل `runInTransaction` باشد.

```ts
// ❌ نادرست — سه تراکنش مستقل؛ شکست دومی، اولی را برنمی‌گرداند
const user = await prisma.user.findUnique({ where: { nationalId } });
if (!user) await prisma.user.create({ data });
await prisma.session.deleteMany({ where: { userId: user.id } });

// ✅ درست — یک واحد اتمیک
await runInTransaction(async (tx) => {
  const user = await tx.user.findUnique({ where: { nationalId } });
  if (!user) await tx.user.create({ data });
  await tx.session.deleteMany({ where: { userId: user.id } });
});
```

### مهلت‌های صریح
`TRANSACTION_DEFAULTS` روی `maxWait: 5s` و `timeout: 10s` تنظیم شده. تراکنشی که
از این مهلت عبور کند خودکار rollback می‌شود، بنابراین یک عملیات کند هرگز
connection pool را قفل نمی‌کند.

### ⚠️ هرگز کار کند داخل تراکنش انجام ندهید
`bcrypt`، `fetch` و فراخوانی S3 هر کدام صدها میلی‌ثانیه تا چند ثانیه طول می‌کشند و
در این مدت قفل ردیف‌ها باز می‌ماند — این **اصلی‌ترین علت deadlock** بود.

```ts
// ✅ الگوی درست: کار سنگین بیرون، تراکنش کوتاه
const passwordHash = await hashPassword(password);   // بیرون از تراکنش
await runInTransaction(tx => tx.user.update({ data: { passwordHash } }));
```

مسیر `onboarding/head-nurse` نمونهٔ کامل این الگو است: حساب در وضعیت `active:false`
رزرو می‌شود → اسناد ابری بیرون از تراکنش ساخته می‌شوند → حساب در تراکنشی جدا فعال
می‌گردد. اگر مرحلهٔ میانی شکست بخورد، حساب غیرفعال می‌ماند و ورود ممکن نیست.

### سطح ایزولاسیون
پیش‌فرض عمداً تعیین نشده تا از `ReadCommitted` پستگرس استفاده شود (کمترین قفل).
برای مواردی که واقعاً باید سریال شوند `runInSerializableTransaction` موجود است؛
شکست سریال‌سازی (`40001`) به‌صورت خودکار تلاش مجدد می‌شود.

## ۲) مکانیزم تلاش مجدد

`lib/db/retry.ts` — عقب‌نشینی نمایی با **full jitter**:

```
تلاش ۱ خطا → صبر ۰..۵۰ms  → تلاش ۲ خطا → صبر ۰..۱۰۰ms → تلاش ۳ ...
```

jitter تصادفی جلوی *thundering herd* را می‌گیرد: بدون آن، چند درخواستی که هم‌زمان
شکست خورده‌اند دقیقاً هم‌زمان دوباره تلاش می‌کنند و باز برخورد می‌کنند.

### چه چیزی تلاش مجدد می‌شود؟

| گذرا (تلاش مجدد ✅) | منطقی (تلاش مجدد ❌) |
|---|---|
| `P2034` بن‌بست/تداخل نوشتن | `P2002` نقض یکتایی |
| `40001` شکست سریال‌سازی | `P2025` رکورد پیدا نشد |
| `40P01` deadlock detected | `P2003` نقض کلید خارجی |
| `P2024` تایم‌اوت connection pool | خطای اعتبارسنجی |
| `P1001/P1017` قطع اتصال | پنیک موتور |
| `database is locked` (SQLite) | |

سقف زمان کل (`totalTimeoutMs`) تضمین می‌کند درخواست کاربر بی‌نهایت معطل نماند.

### پروفایل‌های آماده
`RETRY_PROFILES.read` / `.write` / `.heavy` — به‌ترتیب برای خواندن، نوشتن معمولی و
عملیات سنگین (حذف بخش، انتقال مدیریت).

## ۳) جلوگیری از درخواست‌های تکراری

### چرا `useState` کافی نیست؟
به‌روزرسانی state در React **ناهم‌زمان** است. دو کلیک در یک تیک، هر دو مقدار قدیمیِ
`isSubmitting === false` را می‌بینند و هر دو عبور می‌کنند. `useRef` بلافاصله و
هم‌زمان تغییر می‌کند:

```ts
if (lockRef.current) return;   // کلیک دوم همین‌جا متوقف می‌شود
lockRef.current = true;
try { /* ... */ } finally { lockRef.current = false; }
```

### ابزارها
- **`useSubmitGuard`** (`features/shared/hooks/useSubmitGuard.ts`) — حالت `ignore`
  (دکمهٔ ثبت) یا `queue` (ذخیرهٔ خودکار)، به‌همراه `isRunning` و مدیریت خطا.
- **`withMutex(key)`** (سمت سرور) — درخواست‌های هم‌کلید سریال می‌شوند؛ کلیدهای
  متفاوت موازی می‌مانند. صف بیش از ۱۶ درخواست با ۴۲۹ رد می‌شود.
- **`runIdempotent(key)`** — نتیجهٔ اولین اجرا کوتاه‌مدت کش می‌شود؛ درخواست تکراری
  همان نتیجه را می‌گیرد بدون اجرای دوباره.

### الگوی «پاسخ کهنه»
فهرست‌هایی که هم با تایمر، هم با `focus` و هم دستی بارگذاری می‌شوند (مثل
`ResetRequestList`) از شمارندهٔ نسل استفاده می‌کنند تا پاسخ کند و قدیمی، داده‌های
تازه را بازنویسی نکند:

```ts
const generation = ++generationRef.current;
const data = await fetchJson(url, { signal });
if (generation !== generationRef.current) return;   // پاسخ کهنه، دور ریخته می‌شود
```

## ۴) مدیریت خطا

### قرارداد پاسخ سرور
خطاهای گذرا با `retryable: true` و هدر `Retry-After` برمی‌گردند:

```jsonc
{ "success": false, "code": "DB_TEMPORARILY_UNAVAILABLE",
  "error": "پایگاه داده لحظه‌ای قفل شده است؛ چند ثانیهٔ دیگر تلاش کنید.",
  "retryable": true }
```

| وضعیت | معنی | کلاینت چه می‌کند |
|---|---|---|
| `409` + `retryable` | تداخل نوشتن گذرا | تلاش مجدد خودکار |
| `409` بدون `retryable` | تداخل واقعی (کد ملی تکراری) | نمایش پیام به کاربر |
| `429` | درخواست هم‌زمان بیش از حد | صبر طبق `Retry-After` |
| `503` | قفل/اتصال/pool | تلاش مجدد خودکار |
| `500` | خطای واقعاً پیش‌بینی‌نشده | نمایش پیام عمومی |

پیام‌های فارسی همیشه از `classifyDbError` می‌آیند و **هرگز جزئیات داخلی پایگاه
داده را فاش نمی‌کنند**. جزئیات فقط در لاگ سرور با `describeDbError` ثبت می‌شود.

### سمت کلاینت
`resilientFetch` همین قرارداد را رعایت می‌کند:
- `GET/HEAD` → خطای شبکه و ۵xx تلاش مجدد می‌شود.
- `POST/PATCH/DELETE` → **فقط** وقتی سرور صریحاً `retryable: true` گفته باشد یا
  وضعیت ۴۲۹/۵۰۳ باشد. خطای شبکه روی این متدها تکرار **نمی‌شود**، چون ممکن است
  درخواست به سرور رسیده و اعمال شده باشد و فقط پاسخ گم شده باشد.

### بازیابی خودکار در ذخیره‌سازی ابری
مسیر `saveDbState` در `app/page.tsx` دیگر با هر خطایی قفل نمی‌شود:
- **هیچ سندی نوشته نشده** → وضعیت محلی به آخرین مقدار معتبر برمی‌گردد؛ کاربر
  می‌تواند بلافاصله دوباره تلاش کند.
- **نوشتن جزئی** → تلاش خودکار برای همگام‌سازی از سرور؛ فقط اگر آن هم شکست بخورد
  رفتار fail-closed اعمال می‌شود.
- تداخل ETag تا **۳ دور** (با تأخیر تصادفی) به‌صورت خودکار مرج و بازنویسی می‌شود.

## پایش

`GET /api/health` وضعیت پایگاه داده و مدار شکن ذخیره‌سازی را برمی‌گرداند:

```jsonc
{ "status": "ok",
  "database": { "ok": true, "latencyMs": 12 },
  "storage":  { "circuit": "closed", "failures": 0 } }
```

در حالت `degraded` کد ۵۰۳ به‌همراه `Retry-After` برگردانده می‌شود تا لودبالانسر
تا آماده شدن کامل، ترافیک نفرستد.

در محیط توسعه، کوئری‌های کندتر از ۲ ثانیه با `[db-slow]` و هر تلاش مجدد با
`[db-retry]` در کنسول سرور لاگ می‌شوند.
