# تحلیل و بهینه‌سازی زمان لود اولیه

این سند ریشهٔ کندی لود اولیه را مستند می‌کند. تمرکز روی **نقص‌های ساختاری** است،
نه تنظیمات سطحی.

## خلاصهٔ یافته‌ها

| # | مشکل | ریشه | نوع |
|---|---|---|---|
| ۱ | تأخیر و چشمک زدن لوگو | ارجاع به فایل ناموجود `/logo.png` → ۴۰۴ → fallback به SVG ۵۶۴ کیلوبایتی | باگ + دارایی نامناسب |
| ۲ | کندی لود بخش پیش‌فرض | آبشار: فهرست بخش‌ها منتظر پاسخ نشست می‌ماند | معماری |
| ۳ | کندی لود صفحهٔ اصلی | دانلود **همهٔ** برنامه‌های ماهانهٔ تاریخچه | معماری |
| ۴ | دو رفت‌وبرگشت اضافه در هر بار لود | خواندن سریالی اسناد سناریو | کد غیربهینه |
| ۵ | هزینهٔ S3 در هر بازدید صفحهٔ ورود | نبود کش سمت سرور برای فهرست بخش‌ها | نبود کش |
| ۶ | کندی همهٔ درخواست‌ها | Service Worker بی‌فایده که هر درخواست را رهگیری می‌کرد | ضدالگو |

## ۱) لوگو — باگ واقعی، نه فقط کندی

کد قبلی:

```tsx
<img src="/logo.png" onError={/* → /logo.svg → /logo.jpg → /logo.jpeg → 🏥 */} />
```

`public/logo.png` **اصلاً وجود نداشت**. توالی واقعی در هر بار باز کردن صفحهٔ ورود:

```
GET /logo.png  → 404          (رفت‌وبرگشت ۱، هدررفت کامل)
GET /logo.svg  → 200، ۵۶۴KB   (رفت‌وبرگشت ۲)
                              ← ۶۱۲ مسیر برداری، بدون viewBox
                              ← تجزیه و رستر شدن برای نمایش ۸۰ پیکسلی
```

سه اشکال هم‌زمان: یک درخواست کاملاً هدررفته، نیم مگابایت برای نشانی ۸۰ پیکسلی، و
کار سنگین CPU روی رشتهٔ اصلی برای تجزیهٔ SVG.

**اصلاح:** همان تصویر به PNG رستر شد و با `next/image` + `priority` سرو می‌شود.

| | پیش | پس |
|---|---|---|
| رفت‌وبرگشت | ۲ (یکی ۴۰۴) | ۱ (preload در HTML) |
| حجم | ۵۶۴ KB | ۱۰.۵ KB (**۹۸٪ کمتر**) |
| پرش چیدمان | دارد | ندارد (ابعاد صریح) |

`priority` باعث می‌شود Next.js یک `<link rel="preload">` در همان HTML اولیه بگذارد،
پس دانلود لوگو هم‌زمان با تجزیهٔ سند شروع می‌شود نه پس از آن.

نسخهٔ برداری اصلی در `assets/source/logo.svg` بایگانی شد (خارج از `public/` تا
دیگر قابل درخواست از شبکه نباشد). فایل بی‌استفادهٔ `icon-new3.png` (۸۰۸KB) هم حذف
شد. مجموع `public/` از **۱.۶MB به ۲۹۶KB** رسید.

## ۲) آبشار احراز هویت → بخش‌ها

```
پیش:  mount ──▶ GET /api/auth/me ──(تمام)──▶ رندر ──▶ GET /api/public/departments
                └──────── t1 ────────┘              └────────── t2 ──────────┘
      زمان کل = t1 + t2

پس:   mount ──┬─▶ GET /api/auth/me ────────┐
              └─▶ GET /api/public/departments ┴─▶ رندر
      زمان کل = max(t1, t2)
```

علت آبشار، شرط `if (isAuthLoading) return` در افکت دوم بود. اما فهرست بخش‌ها
**عمومی** است و هیچ وابستگی‌ای به نشست ندارد؛ این انتظار کاملاً بی‌دلیل بود.
بدترین حالت برای کاربر مهمان بود: باید منتظر یک پاسخ ۴۰۱ می‌ماند تا تازه واکشی
بخش‌ها شروع شود.

از `Promise.allSettled` استفاده شده تا شکست یکی، دیگری را از بین نبرد.

یک باگ فرعی هم رفع شد: افکت به `selectedDepartmentId` وابسته بود و با هر تغییر
انتخاب بخش، کل واکشی دوباره اجرا می‌شد. حالا با به‌روزرسانی تابعی
(`setSelectedDepartmentId(current => ...)`) این وابستگی حذف شده است.

## ۳) دانلود کل تاریخچه — بزرگ‌ترین مشکل

`readDatabaseState` **همهٔ** برنامه‌های ماهانه را می‌خواند، در حالی که رابط کاربری
فقط ماه جاری را نشان می‌دهد. هر سند ماهانه شامل تخصیص شیفت تمام پرسنل، هشدارها و
لاگ رویدادهاست.

بخشی با دو سال سابقه: **۲۴ سند** دانلود می‌شد تا **۱ سند** نمایش داده شود.

**اصلاح:** پارامتر `?months=` به `GET /api/storage` اضافه شد. کلاینت پنجرهٔ
«ماه قبل، جاری، بعد» را می‌گیرد (ماه‌های همسایه برای ناوبری آنی پیش‌واکشی می‌شوند).

پاسخ اکنون دو فیلد جدید دارد:
- `availableMonths` — همهٔ ماه‌های موجود روی سرور (برای ناوبری تقویم)
- `loadedMonths` — ماه‌هایی که واقعاً در این پاسخ آمده‌اند

### ⚠️ دو خطر داده‌ای که رفع شد

بارگذاری جزئی بدون احتیاط می‌توانست داده را نابود کند:

1. **حذف تصادفی ماه‌ها** — `buildStorageMutations` فقط روی `after.schedules`
   حلقه می‌زند و هرگز چیزی حذف نمی‌کند، پس ماه بارگذاری‌نشده دست‌نخورده می‌ماند.
   این ویژگی اکنون صریحاً مستند شده تا در تغییرات بعدی نشکند.

2. **پیش‌شرط اشتباه در نوشتن** — ماهی که بارگذاری نشده ولی روی سرور هست، با
   `If-None-Match: *` نوشته می‌شد و تداخل می‌گرفت. حالا `existed` علاوه بر وضعیت
   محلی، `availableMonthKeysRef` را هم بررسی می‌کند.

3. **بازنویسی با سند خالی** — `attachEventLogsToDb` اگر برنامهٔ ماه را پیدا
   نمی‌کرد یک سند خالی می‌ساخت. برای ماه بارگذاری‌نشده این یعنی پاک کردن برنامهٔ
   واقعی. اکنون در این حالت ثبت لاگ (که «بهترین تلاش» است) صرف‌نظر می‌شود.

## ۴) خواندن سریالی اسناد سناریو

```ts
// پیش — دو رفت‌وبرگشت کامل، پشت سر هم
const activeScenariosDoc = await readResourceIfExists(activeScenariosResource);
const scenarioVotesDoc   = await readResourceIfExists(scenarioVotesResource);
```

این دو `await` بعد از موج موازی اصلی اجرا می‌شدند و دو رفت‌وبرگشت شبکه به انتهای
مسیر بحرانی اضافه می‌کردند، بدون هیچ وابستگی‌ای بین‌شان. اکنون داخل همان
`Promise.all` قرار گرفته‌اند و هزینهٔ اضافی‌شان صفر است.

## ۵) کش فهرست بخش‌ها

هدر `Cache-Control` که از قبل تنظیم شده بود فقط روی مرورگر/CDN اثر دارد؛ برای
**اولین بازدید هر کاربر** هیچ کمکی نمی‌کرد و هر درخواست یک `GetObject` کامل به S3
می‌زد — روی مسیر بحرانی صفحهٔ ورود.

`lib/cache/department-index.ts` یک کش ۶۰ ثانیه‌ای درون‌حافظه‌ای اضافه می‌کند:
- **حذف هجوم هم‌زمان:** ده کاربر هم‌زمان = یک درخواست S3
- **بازگشت به دادهٔ کهنه:** اگر S3 پایین باشد، آخرین نسخهٔ موفق (تا ۱۰ دقیقه) سرو
  می‌شود تا صفحهٔ ورود کاملاً از کار نیفتد
- **ابطال صریح:** پس از ساخت یا حذف بخش

TTL کوتاه است چون فهرست بخش‌ها تقریباً هرگز تغییر نمی‌کند، ولی وقتی تغییر کرد باید
سریع دیده شود.

## ۶) Service Worker ضدالگو

```js
// پیش — این کد فقط ضرر داشت
self.addEventListener('fetch', (event) => {
  event.respondWith(fetch(event.request));
});
```

هر درخواست از رشتهٔ اصلی به Service Worker و برگشت می‌رفت و مسیر بهینهٔ خود مرورگر
دور زده می‌شد — **بدون هیچ سود کشی**.

نسخهٔ جدید فقط دارایی‌های ایستا (تصاویر و آیکون‌ها) را با راهبرد «کش-اول» نگه
می‌دارد و درخواست‌های API و ناوبری را کاملاً دست‌نخورده رها می‌کند تا هرگز دادهٔ
کهنه یا پاسخ احراز هویت کش نشود.

هدرهای کش بلندمدت هم در `next.config.ts` برای دارایی‌های `public/` اضافه شد.

## جمع‌بندی اثر

**لود صفحهٔ ورود:**
- رفت‌وبرگشت لوگو: ۲ → ۱ (و ۵۶۴KB → ۱۰.۵KB)
- زمان بخش‌ها: `auth + departments` → `max(auth, departments)`
- در بازدیدهای بعدی، فهرست بخش‌ها از کش سرور می‌آید (بدون تماس S3)

**لود صفحهٔ اصلی** (بخش با ۲۴ ماه سابقه):
- اسناد برنامه: ۲۴ → ۳
- رفت‌وبرگشت‌های سریالی سناریو: ۲ → ۰
- کل درخواست‌های S3: ۳۲ → ۱۱ (**۶۶٪ کمتر**)

عدد دقیق به پهنای باند و تأخیر شبکهٔ کاربر بستگی دارد، اما این‌ها کاهش در **تعداد
رفت‌وبرگشت و حجم داده** است که مستقل از محیط اندازه‌گیری شده و در تست‌ها تثبیت
شده‌اند.
